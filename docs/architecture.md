# Architecture

Status: **Stage 0 spikes done, Stage 1 built (2026-10-24).** Spike results are in §8.

## 3. Rendering mechanism (built, Stage 1)

- **Data:** authored widget plugin `family_hub` (`tesserae/widget/family_hub/`). `server.py`
  GETs `{base_url}/api/render/{device}/{page}.json` with the device bearer (2 s timeout, no
  cache on success). On failure it returns the last good payload with `stale: true`, so the wall
  shows "Hub offline · last updated hh:mm". `requires: ["network:family-hub",
  "network:host.docker.internal"]` (the second is for `npm run dev` on the host).
- **Paint:** a canvas **code element** (`id: wall`) binds the widget as a source
  (`sources: [{key: "family_hub", name: "hub", options: {base_url, device, page, token}}]`) and
  runs `tesserae/paint/routine.js`, the same file `/sim` runs. Geometry comes from
  `tesserae/pages/layout.json`; icons from `tesserae/paint/icons.json` (two-tone Phosphor, inline
  SVG, no fetches; the Planner uses the same file). Fonts: `FH Fraunces` / `FH Outfit`, cached in
  Tesserae by the bootstrap (`WALL_FONTS` in `tesserae/service.ts`, `docs/design.md`).
- **Taps:** each row carries `data-on-tap="@slotN"` and `data-touch-id="o{occurrence}-s{slot}"`.
  The element's `actions` map holds `slotN → webhook:{base}/api/tap/{device}/{page}/N?k={token}`
  (config origin, so the provenance gate allows it). Tap regions follow the painted rows, so
  empty slots are not tappable and picture/reader switches need no page change (ADR-9).
- **Calendar band:** Tesserae's own `calendar_day` widget at `layout.calendar`.
- **Page definition:** `tesserae/pages/wall.json`, generated by
  `tesserae/scripts/build-page.ts`, with placeholders `{{BASE_URL}} {{DEVICE}} {{PAGE}}
  {{TOKEN}}`. A unit test fails if it drifts from the builder. Import fills the placeholders
  and re-keys the device token (`ensureWallPage`).
- **Bootstrap** (`src/lib/server/tesserae/service.ts`, on start when
  `TESSERAE_AUTO_BOOTSTRAP=true`, idempotent): set the admin password on a fresh Tesserae, skip
  onboarding, set timezone and the webhook (push) token, mint an MCP token (scraped once from
  the Settings page and stored in `setting`), install the widget if its version differs, pair
  the simulator's fake E1003, import and bind wall pages, then a full repaint.

## 4. Touch → state → glass (built)

1. Tap. Device inverts the region and beeps (tier-0). It reports `(region_id, event_id,
   digest)`; Tesserae dedupes by event id and rejects stale digests.
2. Tesserae POSTs the slot webhook. Family Hub (`src/lib/server/api.ts`): device token from
   `Authorization` or `?k=` → 401/403 → rate limit (10 per 10 s) → body `device_id` must match
   the path → load the last `served_snapshot` for (device, page) → slot → `occurrence_step` →
   `region_id` must name the same occurrence (else 409 `stale_region`) → 4 s dedupe → flip →
   append `completion_event` → `200 {applied, step, state}`.
3. After responding, the repainter (`src/lib/server/tesserae/repaint.ts`) pushes every wall:
   - **patch** (`POST /api/v1/push`) when every changed row is changing for the first time
     since the device's last full frame;
   - **full frame** (`/api/v1/push` then MCP `POST /pages/<id>/push`) when a row changes back,
     the routine switched, the anchor is unknown (start-up) or a push failed (S3b, S3c).
   Pushes are serialised per device and bursts coalesce. A 30 s ticker repaints when a routine
   window opens or closes or the day rolls over.
4. Tesserae re-renders (fresh `render.json`, new snapshot), diffs and stages patch rects; the
   device picks them up on its next linger poll.

### Latency budget (always-on, same host)

| Hop | Target |
|---|---|
| Finger lift → invert + beep | ≤ 0.45 s |
| Tap report → webhook POST | ≤ 0.2 s |
| App commit + respond + push call | ≤ 0.1 s |
| Tesserae re-render | 0.5–1.5 s |
| Device fetches patch (linger poll 1 s or SSE) | ≤ 1 s |
| Partial e-ink refresh | 0.3–0.6 s |
| **Tap → final state on glass** | **≈ 2–3 s** |

Measured values are in `docs/testing.md`: on the Compose stack a patch repaint reaches the
simulated device's framebuffer ~0.97 s after the tap and a full-frame repaint ~2.0 s, before
the panel's own refresh time.

## 5. Data model

See `docs/SPEC.md` §5 for the table list. Key invariants:
- `occurrence` is unique per (template, local date) and never deleted; step titles and icons
  are snapshotted into `occurrence_step` so template edits do not rewrite history.
  "Regenerate today" re-resolves the day type, appends new steps and removes only untouched
  steps that no longer apply.
- Step edits apply to today (owner, 2026-10-31). Adding, editing, reordering or deleting a step
  syncs that routine's occurrence for today, if it exists, the same way as "Regenerate today"
  but keeping the day type it started with. Ticked steps stay. Past days are not touched.
- Deleting a step: one never put on a day is removed; one that was gets `routine_step.deleted_at`
  (migration 0001) and is hidden from the Planner and from new days, so history keeps its FK.
- `completion_event` is append-only and also records `snapshot_id` and `slot` for wall taps.
- Baby plans (ADR-23, migration 0003): a `routine_template` of kind `plan`, excluded from
  `templatesForMember` so it never becomes a wall routine. `routine_step.due_at` /
  `due_after_step_id` + `due_after_min` hold each step's rule; times are worked out on read
  (`domain/plan.ts`), never stored. Correcting a tick's time writes `completed_at` and a
  `completion_event` with action `retime`. A phone tick on a plan repaints only walls on the
  plan screen, as a full frame (its view key holds the whole timetable).
- Timer steps (migration 0004): `routine_step.timer` + `usual_min`; `occurrence_step.completed_at`
  is the start and `ended_at` the stop. History actions `stop`, `unstop`, `retime_end`. A plan
  change now notifies every wall without forcing a full frame: the plan screen's view key changes
  on any change, the home screen's only when the plan button's "asleep since…" line does.
  Dedupe (ADR-14): the same occurrence step tapped again from the same device within 4 s is
  ignored; `dedupe_key` UNIQUE = sha(device, page, slot, step, floor(ts / 4 s)) guards races.
- Repeating list items (ADR-24, migration 0005): date maths in `domain/repeat.ts` (pure, no DB); `domain/lists.ts` arranges items into open / later / done and writes `list_item_log`. `setItemDone` refuses to tick a repeating item. The wall's "done" state for a repeating item is "latest log row is a done within the 2-minute grace"; while in grace it sorts by `due_before`, so the row keeps its slot for an undo.
- `served_snapshot` keeps the last 50 rows per (device, page).
- `planner_session` holds hashed session tokens (Stage 1 shared PIN).
- A routine whose window crosses midnight belongs to the date it starts; display rollover 03:00.
- Day type is resolved at occurrence generation (admin override → calendar → weekly pattern) and stored on the occurrence; steps are filtered by it. A Planner pick on Today regenerates today straight away (ADR-21); weekly-pattern and calendar changes only affect days not yet started.
- Shared lists (`list`, `list_item`, migration 0002, which also creates a "Shopping" list) are
  household-wide. Writes are idempotent: ticking sets a state; adding an item already on the
  list (case and spacing ignored) does nothing if it is open and unticks it if it is ticked.
  Clearing ticked items deletes them. On a phone a one-off ticked in the last 15 min
  (`TICK_GRACE_MS`; owner, 2026-11-25: time to get round the shop. The wall keeps 2 min) stays in its row struck through and a tap puts it back in
  place (owner, 2026-11-25); then it moves to Ticked, and the page reloads itself when the grace
  ends. "Mark done" on a repeating item's page returns to the list (`?done=<item>`), which shows
  "done, next due …" with Undo while that done is within the grace. List writes publish a `change` event on `/api/events`, so
  every open Planner page refreshes live. Nothing on the wall reads lists yet.
  Since ADR-39 (owner, 2026-11-23) the lists are an index, split in two by ADR-40 (2026-11-25):
  `/planner/lists` (shopping and other lists, **All lists**) and `/planner/tasks` (**Coming up**:
  due, overdue and Now items from every list, tickable, only when there are any; then **To-do
  lists**). Each row shows its open count. `?list=<id>` is that list's own page, on its kind's side (back link, `⋯` for settings,
  add as the last row); forms there post to `?list=<id>&/<action>` so a no-JS post lands on the
  same list. Forms carry `listId`; old `/planner/lists/<id>` links, a list on the wrong side and `?view=coming` (to Tasks) redirect.
- Planner tabs and look (ADR-20, ADR-22, ADR-38): four tabs, the same on desktop (header links)
  and phones (bottom bar): **Home** (`/planner`, landing page: `domain/home.ts`), **Routines**
  (`/planner/routines`: today's routines per child, tick, day type), **Lists** (`/planner/lists`
  `/planner/tasks`, `/planner/notes` and `/planner/gifts` behind a Lists · Tasks · Notes · Gifts
  switch on their index pages, ADR-39, ADR-40; the tab reopens the side last used, `localStorage fh-lists-side`) and
  **Settings** (`/planner/settings`). The calendar page (`/planner/calendar`) opens from Home's
  Today and This week cards. Theme, fonts and icons: `docs/design.md`.
- Planner PWA (2026-10-31): `static/manifest.webmanifest` (start `/planner` since ADR-38, standalone,
  shortcuts to Lists, Notes and Routines), icons from `static/icons/storybook.svg` via `scripts/make-icons.ts`,
  iOS `apple-touch-icon` and meta tags in `app.html`. `src/service-worker.ts` precaches the build,
  fetches Planner pages network-first and keeps the last good copy of each (per build, never the
  login page or a redirect). Offline, the layout shows a banner, turns links into full page loads
  so the worker answers them, and blocks form posts. Logging out deletes the saved pages. Service
  workers need HTTPS (or localhost), so on plain-HTTP LAN phones get a home-screen shortcut
  without offline support until ADR-17 is built.
- Board (ADR-30): `domain/board.ts` builds the view (`boardView`, `weekGrid`), `auth/board.ts`
  holds pairing codes (setting `board_pair`) and `board_session` rows; `hooks.server.ts` lets a
  paired screen (`locals.board`) or an adult reach `/board` and `/api/events`.
- Calendar day types (ADR-29): `domain/calendar-days.ts` matches event titles to day types and
  writes `day_override(source=calendar)`; `planner.syncCalendarDays` runs it from the hub every
  5 min, on the Schedule page load and when an adult clears their pick on Routines, and repaints
  if today changed.
- Calendar tab (ADR-19; was on the Today tab): `CALENDAR_DIR` (Compose mounts Tesserae's
  `plugins/calendar_core` at `/calendar:ro`) → `domain/calendar.ts` reads `feeds.json` (enabled
  feeds) and each `feed_<id>.ics`, parses once per file change, and returns today's events plus
  the next 7 days in the household zone. Events from a calendar named after a member show that
  member's glyph. No folder = no calendar section.
- Settings hub (ADR-22, 2026-11-01): `/planner/settings` links to the setup pages (Members,
  Schedule, Devices, and Simulator on a PIN/LAN session only), holds the per-device choices
  (theme Light / Dark / Auto; "Show setup tools here"), household time zone, Change PIN and Log
  out. Setup pages show a "← Settings" link and keep the Settings tab highlighted.
- Phone layout (ADR-22): at ≤ 640 px wide or in the installed app (`display-mode: standalone`)
  `.desk-only` never shows (Devices, Simulator) and `.setup` shows only when "Show setup tools
  here" is on (the "Today is" day-type chips, the Members and Schedule tiles); `.phone-only` is
  the reverse of `.desk-only`. Per-device choices live in `localStorage` (`fh-theme`,
  `fh-setup`, `src/lib/prefs.ts`) and `app.html` applies them before first paint. Setup pages
  still open by address on any device.
- Habit tasks (`task.kind = 'habit'`) keep only a cache of remote state; the health dashboard
  is the record (SPEC §13).

## 6. Security

- Per-device token on `/api/render/*` (bearer) and `/api/tap/*` (bearer or `?k=`, ADR-13);
  SHA-256 at rest, shown once in the Planner. Wrong device's token → 403, unknown → 401.
  The tap token also sits in the Tesserae page document and in Tesserae's webhook logs; both
  stay inside Tesserae's data folder on the LAN host.
- Planner: PIN (6–12 digits), argon2id hash, httpOnly SameSite=Lax session cookie (30 days,
  stored hashed), 5 failures → 15 min lockout. Changing the PIN needs the current PIN (same
  lockout) and signs out every other PIN session; Settings → "Sign out all devices" ends every
  PIN session, the caller's too. Cloudflare Access sessions end at Cloudflare, not here. After
  login the app only redirects to a `/planner` or `/sim` page on its own origin. CSRF: form
  posts must carry an `Origin` with the request's own host (`hooks.server.ts`), which works on
  any LAN address over HTTP (ADR-15); Kit's own check is off (`csrf.trustedOrigins: ['*']`).
  Rate limit per device (burst 10 / 10 s) on `/api/tap` and `/api/button`; malformed JSON
  gets a 400.
- Every response: `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: same-origin` (not `no-referrer`, which makes browsers send `Origin: null`
  on form posts and would fail the CSRF check). No CSP yet: `app.html`'s inline script needs a
  hash first.
- Planner routine-step actions only touch steps of the routine in the URL.
- The offline page cache (service worker) is deleted on logout, on "Sign out all devices", and
  when a navigation lands on the login page (the session ended).
- The kid tablet holds a full adult session (ADR-27); a kid-only session scope is proposed
  (audit 2026-11-05) and waits for the owner.
- Family Hub holds Tesserae's admin password and push token (env) and the MCP token it mints
  (database). They never reach a page or the render JSON.
- Tesserae admin password on; `TESSERAE_SECRET_KEY` pinned; trusted networks not widened.
- Health dashboard credentials (Access service token or bearer) only in Family Hub env.
- Shared pages show no habit detail and no calendar credentials; ICS URL lives in Tesserae.
- SQLite WAL mode in a named volume. Backups (ADR-31): the app takes a `VACUUM INTO` copy once
  per household day and before any pending migration, into `BACKUP_DIR` (default `backups/`
  next to the database, so `data/family-hub/backups/` on Unraid), and runs `integrity_check`
  and `foreign_key_check` on each copy. Backups hold the Tesserae MCP token and the simulator's
  device credentials in plain text: keep them on the share, never in git.

## 8. Spike results (Tesserae 0.475.0, Colima arm64, 2026-10-24)

Spike scripts and notes live in `spikes/` (not part of the app). Source-level findings were read
from the image itself (`/app/app`), since the docs lag the code.

**S0 arm64 image — pass.** `ghcr.io/dmellok/tesserae:0.475.0` pulled in 1 m 45 s, 1.13 GB,
arm64 manifest. Headless Chromium renders. First run needs `/setup` (admin password) and
onboarding can be skipped (`POST /onboarding/skip`).

**S1 portrait canvas — pass.** `POST /api/mcp/pages {w:1404,h:1872}`; `preview.png` is
1404×1872 (1.4 s cold, ~0.3 s warm); `render_report.tap_invalid` empty with a hotspot, origin
`config`. MCP from the Mac is not loopback (Docker bridge), so it needs the MCP token
(`Authorization: Bearer`), minted in Settings → System → MCP. There is **no** server-side
`TESSERAE_MCP_TOKEN` env var.

**S2 widget data path — pass; mechanism changed to code element + widget data.**
- Authored widget `family_hub` installs via `POST /api/mcp/widgets/install` (gzip tarball,
  MCP token) into `data/authored/family_hub/`. `server.py fetch(options, settings, *, ctx)`
  reached the stub through `requires: ["network:<host>"]` (hostname match, no port).
  Fetch 2–20 ms; page render ~0.3 s warm.
- Use `app.plugin_http.fetch_json`, not `net_guard` (that blocks private IPs). The bundled
  `rest_service` and code-element `{url}` sources **block private addresses**, so they cannot
  reach Family Hub. A custom widget is required.
- Error path: the host does not keep last-good for canvas pages. Our `server.py` keeps its own
  last-good file in `ctx["data_dir"]` and returns it with `stale: true`; verified by making the
  stub return 500.
- `ctx` does not reliably carry device or page id, so both are cell options. The bearer token
  is a plugin **setting** with `secret: true` (encrypted at rest), set via
  `POST /settings/plugin-family_hub` (admin session).
- Code element with `sources:[{key:"family_hub", options, name}]` receives the widget's
  `fetch()` result as `ctx.data[name]`; rows with `data-on-tap="@slotN"` resolve through the
  element's `actions` map and count as **config origin**, so webhooks fire. Tap regions follow
  the painted DOM (verified in `render_report`). Chosen over hotspots (ADR-9).

**S3 tap → webhook → push — pass, with two findings.**
- Simulated E1003 (REST, `proto.v=2`, overlay schema 2, `can_stay_awake`) paired via
  `POST /api/v1/device/admin/pairing/issue` + `POST /api/v1/device/register` (rotation 90 →
  portrait). `POST …/tap {digest, region_id, event_id}` → `ok` in 20–60 ms → webhook POST.
- **No custom headers on webhooks.** Body is `{device_id, region_id, touch_event_id, gesture,
  action_spec, timestamp, …}`, `User-Agent: tesserae-button-webhook/1`, fire-and-forget,
  3 s timeout. No page id in the body. Decision: token in the URL query (ADR-13).
- `POST /api/v1/push` needs the global webhook token (Settings → System → Webhook), is
  synchronous (~0.5–1 s render) and produced a **patch** (36×29 px for one checkbox).
- Dedupe by equal `event_id` → `deduped`; unknown digest → `stale`. A tap against an older
  frame with an unchanged tap layout is still accepted (v2), so touch ids carry the occurrence
  id, which changes the layout when the routine changes.
- **S3b patch revert limitation.** The server diffs every new render against the anchor
  frame, while firmware copies rects into its stored framebuffer. A row that changes and then
  changes back is not repainted (`push` returns `no_change`, or the next patch omits it), so
  glass would keep the old state. Not fixable from outside without a fork. Workaround
  (ADR-4): the app tracks which rows changed since the last full frame; a row's first change
  goes out as a patch; a second change, or a routine switch, triggers a full frame
  (S3c: webhook push, then MCP `POST /pages/<id>/push`, which always mints a full frame). Worth
  an upstream issue: diff against anchor + last fetched patch.
- **S3c full frames and tap regions.** An MCP push publishes a full frame but does not compute
  tap regions; it reuses the page's last region map from a page-pipeline render (`/api/v1/push`,
  Send). After a routine switch that leaves stale touch ids. So a full repaint is
  `POST /api/v1/push` (computes regions, may stage a patch) followed by the MCP push
  (~1.9 s together); verified the new ids reach the manifest.
- `webhook_refresh` fallback with `app.button_webhook_refresh_delay_s=0.5` (settings.json only,
  no UI): patch at 1.4–1.7 s (5 clean runs). Primary path is ~0.6 s faster.

**S4 reproducible page — pass.** `GET /api/mcp/pages/<id>/canvas` exported; on a fresh
container (new secret key, empty data) widget install + `POST /pages` + `PUT /pages/<id>/canvas`
restored it with the same `rev` and the same tap regions. Plugin settings (token, base URL) are
not part of the page and are set by the import script.

**S5 calendar — pass.** `calendar_core` reads feeds from `data/plugins/calendar_core/feeds.json`
(also editable in its admin page); a public Google AU-holidays ICS URL rendered in
`calendar_month` and `calendar_day` with no account. Feed fetch is cached 15 min.

**S6 latency baseline — pass.** See `docs/testing.md`. Tap report → patch available:

## 9. Hardware bring-up findings (E1003, firmware 1.62.2, 2026-10-31)

- **Tap maps are keyed by pixel hash (S3d).** Tesserae names the touch-region sidecar
  `<sha256(composition PNG)>.regions.json` and the last render wins. Two devices whose pages
  paint identical pixels (the wall and the simulator) share one tap map, so the E1003's taps
  were dispatched to `/api/tap/sim-wall/...` and rejected. Fix: the render payload carries
  `device_label` (the device's name) and the painter shows it in the footer, so every device's
  frame is unique. Any future surface on the same painter must keep a per-device difference.
- **Patch blob race (S3e).** Taps a second or two apart stage a new patch that deletes the
  previous blob; a device fetching the old blob in that window gets a 500
  (`FileNotFoundError` after the `is_file()` check in `get_frame_patch_blob`) instead of the
  documented 404. The device recovers on a later poll but the tick is slow, and tapped rows
  can stay inverted until a full frame. Upstream issue candidate, alongside S3b/S3c.
- **Tap target = the whole routine row** (owner, 2026-11-02; was checkbox only since
  2026-10-31). Tesserae's tier-0 feedback inverts the whole tap region and a region has one
  rect, so the row goes black for a moment on a tap. The owner chose a bigger target over
  that. Lists screen items keep the box as their target. Home's To do has no tap targets at
  all (owner, 2026-11-02): it is read-only, ticking happens on the Lists screen.
- **Dropped-tap clean-up.** A tap Tesserae drops (`stale`, `unmapped`, `failed`, `error`)
  leaves the device's invert on glass with no repaint coming. `DroppedTapWatch`
  (`src/lib/server/tesserae/dropped-taps.ts`) reads Tesserae's touch log
  (`/devices/touch/<id>/data.json`, admin session) every 3 s for 30 s after any tap and on the
  30 s ticker, and asks for a full frame for that device when a new drop appears. Taps Family
  Hub rejects (other than `deduped`) also get a full frame.
- No routine active → no tap regions on the page; the device still beeps and inverts locally,
  but nothing is reported. Expected, not a fault.
